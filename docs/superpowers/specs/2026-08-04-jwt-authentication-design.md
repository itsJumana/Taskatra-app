# Taskatra JWT Authentication — Design

## Context

Taskatra currently uses the authentication generated by Rails 8's
`bin/rails generate authentication`: a database-backed `sessions` table plus a
signed, httponly `session_id` cookie. `Authentication#resume_session`
(`app/controllers/concerns/authentication.rb`) looks up
`Session.find_by(id: cookies.signed[:session_id])` on every request and assigns
it to `Current.session`; `Current` delegates `user` to that session.
`ApplicationCable::Connection` reads the same signed cookie independently.

This spec replaces that session-carrying layer with a JWT. **Password handling
is out of scope and does not change** — `has_secure_password`,
`User.authenticate_by`, bcrypt, and the password-reset mailer flow all stay
exactly as they are. Only how an authenticated identity is carried between
requests changes.

## Why, and what this deliberately does not buy

The motivation is to replace the browser session auth itself with JWT, not to
serve an API or a future service split (the microservices split described in
`docs/superpowers/specs/2026-06-30-services-scaffold-design.md` remains paused).

Two things are worth stating plainly, because they are consequences of that
goal rather than oversights:

1. **This is not a security upgrade over the status quo.** The current signed
   httponly cookie is already tamper-proof and XSS-inaccessible. JWT trades
   instant server-side revocation for self-contained claims.
2. **The usual "stateless means no database query" benefit does not apply
   here.** `ApplicationController#resolve_layout` calls `current_user` on every
   request to pick a layout, and the authenticated layout renders user details.
   The user row loads on essentially every request regardless, so token
   verification that also needs the user costs no extra query.

Point 2 is what makes the chosen revocation strategy cheap.

## Decisions

| Decision | Choice | Rationale |
|---|---|---|
| Transport | httponly cookie, **not** `localStorage` | A browser performing a normal navigation to `/projects` cannot attach an `Authorization` header. Cookie transport keeps full-page Turbo navigation, Turbo Streams, form posts, and Action Cable working with zero JavaScript changes. |
| Revocation | `users.token_version` integer | Bumping it invalidates every token for that user, covering the password-reset case. Costs no extra query (see point 2 above). |
| `sessions` table | Dropped | Unused once `token_version` is the revocation mechanism. Nothing in the app reads its `ip_address` / `user_agent` columns. |
| Library | `jwt` gem | Correct `exp` validation and, critically, resistance to algorithm-confusion attacks (`alg: none`, RS256→HS256) that hand-rolled verifiers routinely get wrong. |
| Code structure | `AuthToken` value object in `app/models/` | `Current` already delegates `user` to a session object, so an `AuthToken` slots into the same shape. Keeps the concern thin and the claim logic in one testable, Rails-decoupled file. |

### Accepted trade-offs

These follow directly from the decisions above and are accepted, not deferred:

- **Logout does not invalidate the token.** `terminate_session` deletes the
  cookie, which logs that browser out, but a token copied off the wire stays
  valid until `exp`. Per-device revocation is not achievable with
  `token_version` alone.
- **No per-device logout** and **no login ip / user-agent history** once
  `sessions` is dropped.
- **Everyone is logged out once, on deploy.** Existing `session_id` cookies
  become meaningless when the table is dropped. Relevant to the Kamal rollout.

If per-device revocation is wanted later, the upgrade path is to reintroduce a
`sessions` row as a `jti` registry and add a `jti` claim — the `AuthToken`
boundary makes that a localized change.

## Token format

Signed with **HS256**, pinned explicitly on decode so a forged `alg` header
cannot downgrade verification.

```
{ "sub": <user.id>, "tv": <user.token_version>, "iat": …, "exp": … }
```

- `sub` — user id
- `tv` — `token_version` at issue time; compared against the user's current
  value on every request
- `exp` — 30 days from issue, matching the current cookie's expiry

**Signing key:** `Rails.application.key_generator.generate_key("jwt auth token", 32)`.
Derived from `secret_key_base`, so there is no new credential to provision or
rotate, but domain-separated from the cookie signing key — a leaked JWT key
cannot forge signed cookies and vice versa.

**Cookie:** `cookies[:auth_token]` — plain, not `cookies.signed`, since the JWT
carries its own signature and double-signing adds nothing. Attributes:
`httponly: true`, `same_site: :lax`, `secure` in production, `expires` 30 days.

Rails' CSRF protection is unaffected and stays enabled — it is still required,
because auth rides in a cookie.

## Data flow

**Login / registration** — verify the password exactly as today, then
`AuthToken.encode(user)` and set the cookie.

**Every request** — `Authentication#resume_session` reads the cookie →
`AuthToken.decode` verifies signature and `exp` → loads the user by `sub` →
compares the token's `tv` against `user.token_version`. Any failure (missing
cookie, bad signature, expired, unknown user, `tv` mismatch) yields an
unauthenticated request: the cookie is deleted and the user is redirected to
`new_session_path`, preserving the existing `return_to_after_authenticating`
behavior.

**Action Cable** — `Connection#set_current_user` runs the same decode over
`cookies[:auth_token]`, rejecting the connection on failure.

**Logout** — delete the cookie.

**Password reset** — `@user.increment!(:token_version)` replaces
`@user.sessions.destroy_all`, invalidating every outstanding token for that
user.

## Files

**New**

- `app/models/auth_token.rb` — the `AuthToken` value object: `.encode(user)`,
  `.decode(string)`, and the claim/expiry rules.
- `db/migrate/…_add_token_version_to_users.rb` —
  `integer :token_version, null: false, default: 0`.
- `db/migrate/…_drop_sessions.rb` — drops the table and its foreign key.

**Modified**

- `Gemfile` — add `gem "jwt"`.
- `app/controllers/concerns/authentication.rb` — cookie/JWT decode replaces
  `Session.find_by`; `start_new_session_for` is renamed `issue_auth_token_for`.
- `app/models/current.rb` — `attribute :auth_token`, with `user` delegated to it.
- `app/channels/application_cable/connection.rb` — decode the JWT cookie.
- `app/controllers/passwords_controller.rb` — `increment!(:token_version)`.
- `app/controllers/sessions_controller.rb`,
  `app/controllers/registrations_controller.rb` — renamed issuer call.
- `app/models/user.rb` — drop `has_many :sessions`.

**Deleted**

- `app/models/session.rb`

Controllers, views, and `ProjectPolicy` need no changes: they reach identity
through `Current.user` / `current_user`, whose contract is unchanged.

## Verification

No test framework is configured in this project (MiniTest is disabled in
`config/application.rb`), so verification is static analysis plus a manual pass:

- `bin/rubocop` and `bin/brakeman` clean.
- `bin/rails db:prepare` applies both migrations; `db/schema.rb` regenerates
  with `token_version` present and `sessions` gone.
- Register a new user → lands authenticated.
- Log out → redirected to login; protected pages inaccessible.
- Log in → authenticated; `authenticated` layout renders.
- Reset a password while logged in elsewhere → the other browser is logged out
  on its next request.
- Tamper with the `auth_token` cookie → rejected, redirected to login.
- Hand-craft an expired token → rejected.
- Drag a task on the Kanban board → Turbo Stream broadcast still arrives,
  confirming Action Cable authenticates against the JWT cookie.

## Out of scope

- Bearer-token / `Authorization` header support for API or mobile clients.
- Refresh tokens and short-lived access tokens.
- Per-device session management or a "recent logins" screen.
- Any change to password hashing, the password-reset mailer, or rate limiting.
- Sharing the token with the paused microservices split.
