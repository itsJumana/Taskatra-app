# TaskFlow — Project Plan

A collaborative task management system for software engineering teams.

## Stack (already in place)

- **Rails 8.1.3** · PostgreSQL · Ruby 3.4
- **Solid Cache / Solid Queue / Solid Cable** — no Redis, no Sidekiq
- **Hotwire** (Turbo + Stimulus) · Propshaft · ImportMap
- **Docker** (local) + **Kamal** (production)

---

## 1. Feature Breakdown

### Phase 1 — MVP

| Feature | Technology | Rationale |
|---|---|---|
| Authentication (email/password) | Rails 8 `rails generate authentication` | Built-in, no Devise; creates User + Session models with `has_secure_password` |
| Projects (create, invite members) | PostgreSQL + Turbo Frames | Core domain object; memberships are a join table with roles |
| Task CRUD (title, description, status, priority, due date, assignee) | PostgreSQL + Turbo Frames | Core domain; Turbo Frames for inline editing without full page reloads |
| Kanban board (drag tasks between columns) | Stimulus + Turbo Streams | Stimulus handles drag events; Turbo Streams broadcast column changes to all viewers |
| Real-time board updates | Solid Cable + Action Cable + Turbo Streams | DB-backed cable adapter; Turbo Streams pushed over WebSocket when tasks change |
| Task comments | PostgreSQL + Turbo Streams | Appends new comments in real-time to all viewers of the task |
| In-app notifications | Solid Queue + PostgreSQL + Turbo Streams | Async job creates notification records; Turbo Stream pushes badge update to user channel |
| Activity log (who changed what) | Solid Queue + PostgreSQL | `ActivityLogJob` writes audit trail asynchronously — off the critical path |

### Phase 2 — Enhancements

| Feature | Technology | Rationale |
|---|---|---|
| Labels / tags on tasks | PostgreSQL (join table) | Pure relational; indexed for fast label-based filtering |
| Task dependencies (blocks/blocked-by) | PostgreSQL (self-join) | Adjacency-list self-referential FK on tasks table |
| Subtasks | PostgreSQL (`parent_id` on tasks) | Same tasks table, recursive `parent_id`; rendered as nested Turbo Frames |
| Bulk task import (CSV) | Solid Queue + Ractors | CSV parsing/validation distributed across Ractors; persisted in a single job |
| Project dashboard / stats | Solid Cache + PostgreSQL | Aggregated counts cached in Solid Cache; invalidated on task mutations |
| Email notifications | Solid Queue + ActionMailer | `NotificationDeliveryJob` enqueues async mail delivery via ActionMailer |
| Search | PostgreSQL full-text search (`tsvector`) | GIN-indexed `tsvector` on tasks; no Elasticsearch dependency |

### Phase 3 — Nice-to-Have

| Feature | Technology | Rationale |
|---|---|---|
| GitHub PR/branch linking | External API + Solid Queue | Webhook receiver job fetches PR metadata, links to tasks by convention (`TF-123`) |
| Story points & sprint planning | PostgreSQL + Solid Cache | Sprint table; cached velocity calculations per sprint |
| Time tracking | PostgreSQL | `time_entries` table with start/stop timestamps per task per user |

## 2. Database Schema

### `users`
```
id              bigserial    PK
email           text         NOT NULL UNIQUE
name            text         NOT NULL
password_digest text         NOT NULL
avatar_url      text
created_at      timestamptz  NOT NULL
updated_at      timestamptz  NOT NULL

INDEX: users_email_idx UNIQUE (email)
```

### `sessions`  *(generated by `rails generate authentication`)*
```
id          bigserial    PK
user_id     bigint       NOT NULL FK → users(id) ON DELETE CASCADE
token       text         NOT NULL UNIQUE
ip_address  text
user_agent  text
created_at  timestamptz  NOT NULL
updated_at  timestamptz  NOT NULL

INDEX: sessions_token_idx   UNIQUE (token)
INDEX: sessions_user_id_idx (user_id)
```

### `projects`
```
id          bigserial    PK
name        text         NOT NULL
slug        text         NOT NULL UNIQUE
description text
status      text         NOT NULL DEFAULT 'active'   -- active | archived
owner_id    bigint       NOT NULL FK → users(id)
created_at  timestamptz  NOT NULL
updated_at  timestamptz  NOT NULL

INDEX: projects_slug_idx     UNIQUE (slug)
INDEX: projects_owner_id_idx (owner_id)
```

### `project_memberships`
```
id          bigserial    PK
project_id  bigint       NOT NULL FK → projects(id) ON DELETE CASCADE
user_id     bigint       NOT NULL FK → users(id)    ON DELETE CASCADE
role        text         NOT NULL DEFAULT 'member'   -- owner | member | viewer
created_at  timestamptz  NOT NULL
updated_at  timestamptz  NOT NULL

INDEX: pm_project_user_idx UNIQUE (project_id, user_id)
INDEX: pm_user_id_idx      (user_id)
```

### `tasks`
```
id          bigserial    PK
project_id  bigint       NOT NULL FK → projects(id) ON DELETE CASCADE
creator_id  bigint       NOT NULL FK → users(id)
assignee_id bigint                FK → users(id)    ON DELETE SET NULL
parent_id   bigint                FK → tasks(id)    ON DELETE CASCADE  -- subtasks
title       text         NOT NULL
description text
status      text         NOT NULL DEFAULT 'backlog'
            -- backlog | todo | in_progress | in_review | done | cancelled
priority    integer      NOT NULL DEFAULT 2
            -- 0=urgent  1=high  2=medium  3=low
position    integer      NOT NULL DEFAULT 0   -- ordering within a Kanban column
due_date    date
created_at  timestamptz  NOT NULL
updated_at  timestamptz  NOT NULL

INDEX: tasks_project_status_idx (project_id, status)
INDEX: tasks_assignee_id_idx    (assignee_id)
INDEX: tasks_parent_id_idx      (parent_id)
INDEX: tasks_due_date_idx       (due_date) WHERE due_date IS NOT NULL  -- partial
INDEX: tasks_fts_idx  USING GIN (to_tsvector('english', title || ' ' || COALESCE(description, '')))
```

The GIN full-text index enables keyword search without an external engine.

### `labels`
```
id          bigserial    PK
project_id  bigint       NOT NULL FK → projects(id) ON DELETE CASCADE
name        text         NOT NULL
color       text         NOT NULL   -- hex string, e.g. "#3B82F6"
created_at  timestamptz  NOT NULL
updated_at  timestamptz  NOT NULL

INDEX:  labels_project_id_idx           (project_id)
UNIQUE: labels_project_name_unique_idx  (project_id, name)
```

### `task_labels`
```
id        bigserial  PK
task_id   bigint     NOT NULL FK → tasks(id)  ON DELETE CASCADE
label_id  bigint     NOT NULL FK → labels(id) ON DELETE CASCADE

INDEX: task_labels_unique_idx  UNIQUE (task_id, label_id)
INDEX: task_labels_label_id_idx       (label_id)
```

### `comments`
```
id         bigserial    PK
task_id    bigint       NOT NULL FK → tasks(id) ON DELETE CASCADE
user_id    bigint       NOT NULL FK → users(id)
body       text         NOT NULL
created_at timestamptz  NOT NULL
updated_at timestamptz  NOT NULL

INDEX: comments_task_id_idx (task_id)
```

### `task_activities`
```
id        bigserial    PK
task_id   bigint       NOT NULL FK → tasks(id) ON DELETE CASCADE
user_id   bigint                FK → users(id) ON DELETE SET NULL
action    text         NOT NULL
          -- created | status_changed | assigned | priority_changed
          -- commented | due_date_changed
old_value text
new_value text
created_at timestamptz NOT NULL
-- No updated_at: immutable audit log

INDEX: activities_task_id_idx    (task_id)
INDEX: activities_created_at_idx (created_at)
```

### `notifications`
```
id               bigserial    PK
user_id          bigint       NOT NULL FK → users(id)  ON DELETE CASCADE
notifiable_type  text         NOT NULL   -- 'Task' | 'Comment'
notifiable_id    bigint       NOT NULL
actor_id         bigint                FK → users(id) ON DELETE SET NULL
action           text         NOT NULL
                 -- assigned | commented | status_changed | due_soon
read_at          timestamptz            -- NULL = unread
created_at       timestamptz  NOT NULL

INDEX: notifications_user_unread_idx  (user_id, read_at) WHERE read_at IS NULL
INDEX: notifications_notifiable_idx   (notifiable_type, notifiable_id)
```

The **partial index** on `(user_id, read_at) WHERE read_at IS NULL` makes the unread-count query O(unread rows) instead of O(all rows) — this runs on every page render.

## 3. API Design

### REST Routes

```ruby
# Authentication (Rails 8 built-in)
resource  :session,      only: [:new, :create, :destroy]
resource  :registration, only: [:new, :create]
resource  :password,     only: [:new, :create, :edit, :update]  # reset flow

# Users
resource  :profile, only: [:show, :edit, :update]

# Projects (slug as param for human-readable URLs)
resources :projects, param: :slug do
  resources :tasks,       shallow: true
  resources :labels,      shallow: true
  resources :memberships, only: [:index, :create, :destroy]
end

# Task sub-resources (shallow routes from above, plus dedicated update endpoints)
resources :tasks, only: [] do
  resources :comments,   only: [:create, :edit, :update, :destroy]
  resources :activities, only: [:index]
  resource  :assignment, only: [:update]   # PATCH /tasks/:id/assignment
  resource  :status,     only: [:update]   # PATCH /tasks/:id/status
end

# Notifications
resources :notifications, only: [:index] do
  collection { patch :mark_all_read }
  member     { patch :mark_read }
end
```

Dedicated `resource :status` and `resource :assignment` endpoints exist because status changes and assignments each have distinct domain logic, business rules, and broadcast behaviour — they should not be conflated with a generic task `update`.

### Action Cable Channels

Both channels are implemented via **`Turbo::StreamsChannel`** — we do not write raw Action Cable channel classes. Broadcasting happens from model `after_commit` callbacks.

**`ProjectChannel`** — one subscription per project board viewer
```
Stream name:  "project_#{project.id}"
Triggers:     Task after_create_commit, after_update_commit, after_destroy_commit
Broadcasts:   Turbo Stream HTML fragments — task card updates, column header counts
```

**`NotificationChannel`** — one subscription per logged-in user
```
Stream name:  "notifications_user_#{user.id}"
Triggers:     Notification after_create_commit
Broadcasts:   Turbo Stream updating unread badge count + appending toast element
```

## 4. Background Jobs

All jobs inherit from `ApplicationJob` (`:solid_queue` adapter, runs inside Puma via `SOLID_QUEUE_IN_PUMA=true`).

### `ActivityLogJob`
- **Queue:** `:low`
- **Trigger:** `Task` `after_commit` on create/update
- **Does:** Inserts a `TaskActivity` row with the before/after diff. Async because an audit-trail write has no business being on the request critical path.

### `NotificationDeliveryJob`
- **Queue:** `:default`
- **Trigger:** `Task` `after_commit` (assigned, status changed); `Comment` `after_create_commit`
- **Does:** Determines target users, creates `Notification` records, broadcasts a Turbo Stream to each user's notification stream, enqueues `NotificationMailJob` per user with email enabled.

### `NotificationMailJob`
- **Queue:** `:mailers`
- **Trigger:** Enqueued by `NotificationDeliveryJob`
- **Does:** Renders and delivers the notification email via ActionMailer. Separate job so an SMTP failure retries only the mail, not the whole notification creation.

### `TaskDueSoonJob`
- **Queue:** `:scheduled`
- **Trigger:** `config/recurring.yml` — daily at 09:00
- **Does:** `tasks WHERE due_date = CURRENT_DATE + 1 AND status NOT IN ('done','cancelled')` → enqueues `NotificationDeliveryJob` for each with `action: 'due_soon'`.

### `StaleTaskReminderJob`
- **Queue:** `:scheduled`
- **Trigger:** `config/recurring.yml` — every Monday at 08:00
- **Does:** Finds `in_progress` tasks with no `task_activities` in the last 7 days. Enqueues reminders to assignees. Automated WIP discipline without manual nagging.

### `ProjectStatsCacheWarmJob`
- **Queue:** `:low`
- **Trigger:** `Task` `after_commit` on any status change
- **Does:** Recalculates project stats (task counts by status) and writes to Solid Cache immediately. Keeps the cache warm proactively rather than invalidating and waiting for the next miss.

### `BulkTaskImportJob`
- **Queue:** `:default`
- **Trigger:** `POST /projects/:slug/imports` (manual CSV upload)
- **Does:** Parses/validates CSV rows using Ractors (see §6), bulk-inserts valid tasks via `Task.insert_all!`, broadcasts import results back to the uploader's browser via Turbo Stream.

## 5. Caching Strategy

All caching via **Solid Cache** (database-backed, 256 MB limit, `taskflow_production_cache` DB).

Pattern used throughout: `Rails.cache.fetch(key, expires_in: TTL) { query }` in service objects — never in models or controllers directly.

| Cache Key | TTL | Invalidated By | Why |
|---|---|---|---|
| `projects/#{id}/stats` | 5 min | `ProjectStatsCacheWarmJob` after task commit | Expensive `COUNT GROUP BY status` query; shown on dashboards |
| `users/#{id}/projects` | 10 min | Explicit delete in `ProjectMembership` callbacks | Powers the sidebar on every page; changes are rare |
| `projects/#{slug}/labels` | 1 hour | Explicit delete in `Label` callbacks | Fetched on every task view; labels rarely change |
| `tasks/#{id}` | 2 min | `touch: true` propagation on task update | Individual task data for fast re-renders |
| `notifications/unread_count/#{user_id}` | Until invalidated | Explicit delete in `Notification` after_create/after_update | Displayed in nav on every page — must be fast |

**Why not Redis?** Solid Cache uses the existing PostgreSQL infrastructure. For this scale, the DB serves cached reads faster than a cold Redis call when indexes are good. Redis adds operational overhead with no benefit below ~10k req/min.

## 6. Ractors Usage

Ractors bypass the GVL for true parallelism. Hard constraint: **Active Record is not Ractor-safe**. All DB I/O stays on the main thread. Ractors are used only for CPU-bound, side-effect-free transformations on frozen plain-Ruby objects.

### BulkTaskImportJob — Parallel CSV Parse + Validate

```ruby
rows   = CSV.parse(csv_string, headers: true).map(&:to_h)  # frozen hashes
chunks = rows.each_slice(50).to_a

ractors = chunks.map do |chunk|
  Ractor.new(chunk) do |rows|
    rows.map { |row| TaskImportValidator.validate(row) }  # pure Ruby, no AR
  end
end

results     = ractors.map(&:take).flatten
valid, errs = results.partition { |r| r[:valid] }
Task.insert_all!(valid.map { |r| r[:attributes] })  # back on main thread
```

`TaskImportValidator` is a plain Ruby class with no AR calls. It validates presence, types, and enum membership against frozen constants. On a 4-core machine, a 1000-row import processes the parse/validate phase in ~25% of single-threaded time.

### Notification Fanout — Parallel Payload Building

When a task update triggers notifications for 40+ project members, payload serialization (template rendering) is CPU-bound:

```ruby
member_ids.each_slice(10).map do |ids|
  Ractor.new(ids, task_data) do |ids, task|  # task_data is a frozen Hash
    ids.map { |id| NotificationSerializer.build(user_id: id, task: task) }
  end
end.flat_map(&:take)
```

**Rule of thumb:** If you need Active Record, don't use a Ractor. If you need a Ractor, extract a plain-Ruby frozen value object first.

## 7. Frontend Approach

### Tailwind CSS

Add `gem "tailwindcss-rails"` — ships the Tailwind CLI as a binstub, generates `app/assets/builds/tailwind.css`. The `bin/dev` Procfile runs the CSS watcher alongside Puma in development. In production, unused classes are purged → ~10 KB output. No CDN, no npm.

### Turbo

| Layer | Used For |
|---|---|
| **Turbo Drive** | All page navigations (no full reloads) |
| **Turbo Frames** | Inline task editing, comment form, task detail drawer, modal content |
| **Turbo Streams** | Real-time pushes from Action Cable (task moves, new comments, notification badge); also form submission error/flash responses |

### Stimulus Controllers

| Controller | Responsibility |
|---|---|
| `kanban_controller` | Drag-and-drop task cards between columns; fires `PATCH /tasks/:id/status` on drop |
| `modal_controller` | Open/close task detail drawer; manages focus trap and scroll lock |
| `dropdown_controller` | Assignee picker, label picker, priority selector |
| `notification_controller` | Marks notification read on click, auto-dismisses toasts after timeout |
| `character_count_controller` | Live character countdown on comment textarea |

### Layout

- **Sidebar** — project list (rendered server-side from cached data)
- **Kanban board** — primary project view; 5 columns: backlog · todo · in_progress · in_review · done
- **Task drawer** — slides in from the right as a Turbo Frame; loaded lazily on task click, no route change
- No client-side routing — Turbo Drive + Turbo Frames handle everything

### React Upgrade Path

The REST routes map directly to a JSON API. To support React later, add `respond_to { |f| f.html; f.json { render json: TaskSerializer.new(task) } }` to controllers. Schema and domain logic are unchanged.

## 8. Deployment Plan (Kamal)

### Prerequisites
1. A VPS (Hetzner CX22 or equivalent — 4 GB RAM, 2 vCPUs)
2. Docker installed on the VPS
3. A container registry (GitHub Container Registry recommended)
4. A domain with DNS A record pointed at the VPS IP

### config/deploy.yml Updates

```yaml
servers:
  web:
    - <VPS IP>

registry:
  server: ghcr.io
  username: <github-username>

proxy:
  ssl: true
  host: taskflow.yourdomain.com

accessories:
  db:
    image: postgres:17-alpine
    host: <VPS IP>
    port: "127.0.0.1:5432:5432"
    env:
      secret: [POSTGRES_PASSWORD]
    directories:
      - data:/var/lib/postgresql/data
```

### Deploy Steps

```bash
# First deploy (provisions server, starts accessories, boots app)
bin/kamal setup

# Subsequent deploys (zero-downtime rolling restart)
bin/kamal deploy

# Instant rollback to previous image
bin/kamal rollback
```

### Secrets (`.kamal/secrets`)

```bash
RAILS_MASTER_KEY=$(cat config/master.key)
KAMAL_REGISTRY_PASSWORD=$KAMAL_REGISTRY_PASSWORD
POSTGRES_PASSWORD=$POSTGRES_PASSWORD
```

### Database in Production

All 4 PostgreSQL databases (`taskflow_production`, `_cache`, `_queue`, `_cable`) are created automatically by `db:prepare` in the Docker entrypoint. The Kamal PostgreSQL accessory hosts all 4 on the same Postgres instance using the `taskflow` role.
